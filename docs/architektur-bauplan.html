Wie Torball-Turniere gebaut ist

Eine Anwendung, um Torball-Turniere zu planen und während des Turniers am Rechner zu protokollieren — für eine Sportart, die von blinden und sehbehinderten Menschen gespielt wird.

Dieser Bauplan zeigt, aus welchen Modulen das System besteht, wie eine Anfrage durch die Schichten läuft und wie die Daten zusammenhängen. Alle Zahlen sind aus dem Quelltext des aktuellen main-Standes gezählt, nicht geschätzt. Jede Abbildung lässt sich anklicken und stufenlos vergrößern.

Schichten: von der Browserzeile bis zur Datenbank

Dieselbe gebaute Anwendung läuft in drei Umgebungen — und der Unterschied liegt nicht im Code, sondern darin, wer das Frontend ausliefert und wie /api die Routen erreicht. Genau an dieser Stelle steckte einer der teuersten Fehler des Projekts: Instanz-zu-Instanz-Aufrufe ohne /api-Präfix landeten bei der SPA-Auslieferung und bekamen HTML statt JSON zurück.

Module: drei Workspaces und eine folgenreiche Grenze

Das Repository ist ein Monorepo mit drei npm-Workspaces. shared hält die Typen, die Backend und Frontend gemeinsam benutzen — aber es wird als CommonJS kompiliert. Das Backend darf daraus echte Funktionen importieren, das Frontend nur Typen, die beim Kompilieren verschwinden.

Diese eine Grenze erklärt eine Eigenheit, über die sonst jeder stolpert: Drei Stück Geschäftslogik existieren absichtlich doppelt — als kleine, identische Kopie auf beiden Seiten. Wer eine davon ändert, muss die andere mitziehen.

Zugriff: eine Anfrage und die Frage, wer sie stellen darf

Es gibt keine Tokens im Browserspeicher: Beim Anmelden entsteht ein Zufallswert, gespeichert wird nur dessen Prüfsumme als Dokument-ID. Ein Gerät ist entweder als Person angemeldet oder per Turnier-Code — nie beides. Aus dieser einen Unterscheidung leitet das System pro Turnier eine von drei Stufen ab.

Zwei Sperren gelten zusätzlich und unabhängig von der Stufe: ein abgeschlossenes Turnier ist schreibgeschützt, und ein an eine lokale Installation verliehenes Turnier ebenfalls — sonst würde die nächste Synchronisierung die Serveränderung ohnehin überschreiben.

Daten: eine Datenbank, 29 Dokumenttypen

Es gibt keine Tabellen und keine Fremdschlüssel, die eine Datenbank erzwingt. Alle Dokumente liegen in einer einzigen CouchDB und werden über ein Feld docType unterschieden — in TypeScript zusammengefasst als ein großer Vereinigungstyp TorballDokument. Beziehungen sind schlicht Felder, die eine fremde Dokument-ID enthalten.

Das hat eine Konsequenz, die im Diagramm nicht sichtbar ist, aber überall im Code steckt: Löschen muss von Hand kaskadieren. Wer ein Turnier löscht, muss dessen Mannschaften, deren Spieler, die Schiedsrichter, Spiele, Protokolle und Ereignisse einzeln mitnehmen — die Datenbank tut es nicht.

Fallstrick, der im Modell nicht sichtbar istDie Abfragesprache von CouchDB liefert ohne ausdrückliche Obergrenze nur die ersten 25 Treffer — stillschweigend. Deshalb greift kein Modul direkt auf die Datenbank zu, sondern ausschließlich über die Helfer in repository.ts, die intern korrekt weiterblättern.

Zwei Wege zum selben Ergebnis

Ein Turnier entscheidet sich für einen von zwei Wegen, wie Spielergebnisse entstehen. Der manuelle Weg erfasst nur Endergebnisse — im Formular oder über einen Link, den Helfer ohne Konto öffnen. Der digitale Weg protokolliert jeden Wurf, jedes Foul und jedes Tor als Ereignis und leitet das Ergebnis daraus ab.

Entscheidend für das Verständnis des Systems: Beide Wege münden in dieselben vier Felder am Spiel. Alles, was danach kommt — Tabelle, öffentliche Seite, Ausdrucke — musste für die digitale Protokollierung nicht angefasst werden.

Betrieb: drei Modi, weil die Halle kein Internet hat

Ein Turnier findet in einer Sporthalle statt, und Hallen haben selten verlässliches Netz. Deshalb ist der Offline-Betrieb kein Zusatz, sondern eine tragende Anforderung. Zwei der drei vorgesehenen Modi sind gebaut.

Der aufwendigste Fall ist die Instanz-Kopplung: Ein Turnier wird am Rechner zu Hause geplant und für den Spieltag an eine lokale Installation ausgeliehen. Bewusst kein allgemeiner Abgleich mit Konfliktauflösung, sondern eine strikte Eins-zu-eins-Ausleihe — zu jedem Zeitpunkt ist ein Turnier entweder frei oder bei genau einer Installation.

Tragende Regeln

Sieben Entscheidungen, die man kennen muss, bevor man etwas an diesem System ändert. Jede ist mindestens einmal durch einen echten Fehler bezahlt worden.

  • Immer beide

    Vier Logikbausteine existieren doppelt

    Weil das Frontend aus shared keine Laufzeit-Funktionen beziehen kann, sind Spieldauer, Schiedsrichter-Konflikte, Passwortregeln und der Annullierungs-Filter des Protokolls als identische Kopien auf beiden Seiten abgelegt. Wer eine ändert, muss die andere mitziehen.

  • Nie direkt

    Datenbankzugriff nur über repository.ts

    Eine Mango-Abfrage ohne ausdrückliche Obergrenze liefert stillschweigend nur 25 Treffer. Die Helfer im Repository blättern korrekt durch — ein direkter Aufruf sieht auf dem Testdatenbestand richtig aus und verliert im Turnierbetrieb Daten.

  • Vor dem Merge

    Fremde Felder aus dem Anfragekörper entfernen

    Unbekannte Felder werden vom Server durchgereicht. Jede Route, die den Anfragekörper mit einem bestehenden Dokument verschmilzt, muss _id, _rev und docType vorher abstreifen — sonst lässt sich darüber ein fremdes Dokument anlegen oder ein Passwort-Hash einschleusen.

  • Nur Server

    Zuschreibungen setzt niemals der Client

    Wer etwas angelegt, zuletzt bearbeitet oder abgeschlossen hat, entscheidet ausschließlich der Server. Diese Felder werden aus eingehenden Daten entfernt, bevor sie übernommen werden.

  • Vier Prüfungen

    Jede neue turnierbezogene Schreibroute braucht dasselbe Gerüst

    Zugriffsstufe prüfen, auf abgeschlossenes Turnier prüfen, auf ausgeliehenes Turnier prüfen — und die Bearbeitungsspur des Turniers nachziehen. Fehlt Letzteres, vergisst die Turnierliste die Änderung; fehlt eine der ersten drei, ist es eine Sicherheitslücke.

  • Mitziehen

    Wer das Sync-Paket erweitert, erweitert die Prüfung

    Ein importiertes Dokument wird unter seiner mitgelieferten ID geschrieben. Die Validierung prüft deshalb ID-Präfix, docType und Turnier-Zugehörigkeit einzeln. Ein neuer Dokumenttyp im Paket ohne passende Prüfregel wird entweder fälschlich abgelehnt oder ungeprüft durchgelassen.

  • Unveränderlich

    Ereignisse werden nie geändert und nie gelöscht

    Eine Korrektur im digitalen Protokoll ist immer ein neues Ereignis, das ein früheres für unwirksam erklärt. Gestrichene Einträge bleiben im Spielbericht sichtbar — das ist der Sinn eines Protokolls und keine technische Bequemlichkeit.

Grundhaltung des ganzen SystemsDie Software warnt bei Regelverstößen, aber sie entscheidet nicht. Kein Spielplan-Vorschlag, keine Schiedsrichter-Einteilung und keine Protokoll-Prüfung blockiert je eine Eingabe — die Turnierleitung darf jede Automatik überschreiben. Das ist keine Nachlässigkeit, sondern die bewusste Rollenverteilung zwischen Werkzeug und Mensch.
